### 2.3 关键代码改动

#### 2.3.1 新增 `ToolPathResolver`：统一的“目录内”校验

```java
static File resolveInside(String baseDir, String fileName) {
    if (fileName == null || fileName.trim().isEmpty()) {
        throw new IllegalArgumentException("file name must not be blank");
    }
    Path base = Paths.get(baseDir).toAbsolutePath().normalize();
    Path target = base.resolve(fileName).normalize();
    if (!target.startsWith(base)) {
        throw new IllegalArgumentException("illegal file name: " + fileName);
    }
    return target.toFile();
}
```

要点：`normalize()` 会消解 `../`；`resolve()` 遇到绝对路径直接返回绝对路径，因此也会被 `startsWith` 拦下。工具内部捕获异常并转换成可读错误文案，不向模型抛异常。

#### 2.3.2 文件与 PDF 工具接入校验

- `FileOperationTool`：`FILE_DIR` 改为 `static final`；读写都先 `ToolPathResolver.resolveInside(FILE_DIR, fileName)`，再交给 Hutool 读写。
- `PDFGenerationTool`：目录常量 `PDF_DIR`；先校验文件名与 `content != null`，再创建目录/写文件；`catch (IOException)` 改为 `catch (Exception)`。

#### 2.3.3 联网搜索：少于 5 条不再失败

```java
JSONArray organicResults = jsonObject.getJSONArray("organic_results");
if (organicResults == null) {
    return "Error searching Baidu: missing organic_results";
}
if (organicResults.isEmpty()) {
    return "未搜索到相关结果。";
}
List<Object> objects = organicResults.subList(0, Math.min(5, organicResults.size()));
```

#### 2.3.4 文件记忆：会话 ID 路径校验

```java
if (conversationId == null || conversationId.isBlank() || conversationId.length() > 64) {
    throw new IllegalArgumentException("非法的会话 ID：" + conversationId);
}
Path base = Paths.get(BASE_DIR).toAbsolutePath().normalize();
Path target = base.resolve(conversationId + ".kryo").normalize();
if (!target.startsWith(base)) {
    throw new IllegalArgumentException("非法的会话 ID：" + conversationId);
}
return target.toFile();
```

> 该组件默认未启用（`AftersalesApp` 使用 `MessageWindowChatMemory`）。若后续启用文件记忆，`chatId` 来自 HTTP 参数，必须保留此校验。

#### 2.3.5 `BaseAgent`：实例可复用

```java
private synchronized void startNewRun(String userPrompt) {
    if (this.state == AgentState.RUNNING) {
        throw new IllegalStateException("Cannot run agent from state: " + this.state);
    }
    this.state = AgentState.RUNNING;
    this.currentStep = 0;
    this.messageList.clear();
    this.messageList.add(new UserMessage(userPrompt));
}
```

- `run()` / `runStream()` 都改为调用 `startNewRun()`；`runStream` 中先校验空提示词，再启动。
- 执行结束后**不**把状态强制复位为 `IDLE`：`FINISHED` / `ERROR` 仍可被调用方读取。
- 复用实例会清空 `messageList` 与 `currentStep`，避免上一轮上下文串入下一轮。
- `runStream` 的校验 `catch` 增加了 `return`，避免向已完成的 emitter 继续执行。

## 8. 后续修改：MCP 图片检索改用 SearchAPI（2026-10-18）

### 8.1 背景

Pexels API Key 在官网暂时无法申请，继续使用 Pexels 会阻塞 MCP 图片检索。主项目已经配置 SearchAPI 并验证可用，因此把 MCP 的 `ImageSearchTool` 从 Pexels 切换到 **SearchAPI Google Images**，复用同一把 Key。

### 8.2 改动内容

| 文件 | 类型 | 说明 |
|---|---|---|
| `ecom-mcp-server/src/main/java/com/aftersales/mcp/tools/ImageSearchTool.java` | 修改 | 改为请求 `https://www.searchapi.io/api/v1/search?engine=google_images`；解析 `images[].original.link`，缺失时回退 `thumbnail`，最多返回 5 条；Key 改由构造函数注入 |
| `ecom-mcp-server/src/main/resources/application.yml` | 修改 | 新增 `search-api.api-key: ${SEARCH_API_KEY:}`，不再需要 Pexels Key |
| `ecom-mcp-server/src/test/java/com/aftersales/mcp/tools/ImageSearchToolTest.java` | 重写 | 8 条 Mock 测试：原始字段解析、thumbnail 回退、5 条上限、参数校验、空结果、API error、缺 Key、解析异常 |
| `docs/AI_CONTEXT.md` | 修改 | 密钥表移除 Pexels，补充 MCP 启动与 `SEARCH_API_KEY` 说明 |
| `README.md` | 修改 | 密钥表与 MCP 启动说明同步更新 |

关键解析逻辑：

```java
JSONArray images = json.getJSONArray("images");   // Google Images 返回顶层 images，而不是 images_results
for (Object item : images) {
    JSONObject image = (JSONObject) item;
    String url = image.isNull("original") ? null : extractOriginalUrl(image.get("original"));
    if (StrUtil.isBlank(url)) url = image.getStr("thumbnail");
    ...
}
```

`original` 在 SearchAPI Google Images 中可能是对象（含 `link`/`width`/`height`），也可能是字符串；两种形态都已兼容。

### 8.3 配置与启动

MCP 侧通过环境变量注入 Key（不写进仓库）：

```bash
# macOS / Linux
export SEARCH_API_KEY=你的SearchAPI密钥
cd ecom-mcp-server && mvn spring-boot:run

# Windows PowerShell
$env:SEARCH_API_KEY = "你的SearchAPI密钥"
cd ecom-mcp-server; mvn spring-boot:run
```

stdio 方式由主项目拉起子进程时，`SEARCH_API_KEY` 会从父进程环境继承；也可以显式传入 `--search-api.api-key=...`。

### 8.4 验证结果

- `ImageSearchToolTest`：8/8 通过（Mock HTTP，不消耗 SearchAPI 配额）。
- 真实调用：`searchImage("快递外包装破损")` 返回 5 条 Google Images 图片 URL。
- MCP 服务启动：`8127` 监听、`/sse` 返回 `event:endpoint`、注册工具 1 个。
- 本机离线仓库缺少 Spring Boot 3.4.5 测试依赖，MCP 测试未通过 `mvn test` 执行，而是用临时 JUnit Runner 编译运行；正常联网环境可直接 `mvn test`。

### 8.5 影响与注意

- Pexels Key 不再需要；图片检索与联网搜索共用 `SearchAPI Key`。
- MCP 协议、工具名 `searchImage`、端口 `8127` 均未变化，主项目接入方式不变。
- SearchAPI 的 Google Images 单次返回 100 条，本工具只取前 5 条；结果 URL 可能是第三方站点图片，展示前需自行校验可访问性。
- 若后续 SearchAPI 套餐不包含 Google Images，可把 `engine` 换成 `bing_images` 或 `duckduckgo_images`，解析字段需按对应引擎调整。

| `README.md`、`docs/AI_CONTEXT.md` | 补充控制台/IDE 编码说明 |

### 9.2 原因

字节级验证发现：Logback 日志本身已经是 UTF-8，而 `System.out` 的中文按 `stdout.encoding`（中文 Windows 通常是 GBK）输出。如果控制台按 GBK 解码，UTF-8 日志就会乱码；如果控制台按 UTF-8 解码，GBK 的 stdout 就会乱码。

因此控制台编码默认**跟随 JVM 的 `stdout.encoding`**，与终端/IDE 实际使用的解码方式保持一致；文件日志固定 UTF-8，便于归档和后续 AI 读取。

### 9.3 使用注意

- 默认无需配置：控制台跟随 JVM stdout（Windows 通常 GBK），文件日志 UTF-8。
- 如果 IDE/终端是 UTF-8：设置 `LOG_CHARSET=UTF-8`，或在 VM options 中加 `-Dstdout.encoding=UTF-8`，并确保控制台编码为 UTF-8。
- 如果终端是 GBK：无需设置；必要时可显式设置 `LOG_CHARSET=GBK`。
- 修改后需重启后端才会生效。
