### 3.3 重点验证（全部通过）

1. **终止语义三层**（AI_CONTEXT §5.3/§8 #1-#4）
   - 模型不再调用工具 → `FINISHED` 并返回助手文本；
   - `terminate` 工具 → `FINISHED` 且**优先返回本轮助手文本**（回归 #3）；
   - 达到 `maxSteps` → 超限提示；在最后一步（`maxSteps`）恰好完成时**不误报**超限（回归 #4）；
   - `think` 异常 → `ERROR` 且不再空转（回归 #2）。
2. **SSE 协议**（AI_CONTEXT §6）
   - 事件顺序：`progress("正在处理…")` → 最终答复 → `[DONE]`；
   - 中间步骤与工具调用细节**不下发**前端（回归 #6）；
   - 最大步数时先发送超限提示，再发送 `[DONE]`；模型异常时仍以 `[DONE]` 收尾。
3. **工具调用**
   - 工具执行结果写回上下文、`已调用工具 xxx` 只作为状态文案；
   - 传往模型的 `Prompt` 只注入一次系统消息，且 `DashScopeChatOptions.internalToolExecutionEnabled=false`、工具定义随请求下发——说明"关闭框架内置工具循环、手工执行"的机制有效。
4. **RAG**
   - 三份规则文档切分为 **17 个片段**（退换货 6 / 物流 6 / 商品与价保 5），每个片段都带 `topic` 与 `filename`；
   - 空检索走"转人工"兜底话术；有结果时规则原文注入提示词；
   - `searchPolicy` 参数固定为 `topK=4`、阈值 `0.4`，结果带 `【topic】` 标签。
5. **前端**
   - 轻量 Markdown 渲染的 **XSS 转义**（`<script>`、`<img onerror>`、加粗内注入均被转义）；
   - `[DONE]` 哨兵、中文参数 URI 编码、错误时关闭 `EventSource`；
   - 路由重定向（`/aftersales`、`/agent`、未知路径回首页）与"用户消息纯文本、AI 消息受控渲染"的约定。

## 4. 缺陷详情

> 以下缺陷均有对应用例：首轮执行时 6 条用例失败；经用户确认后已全部修复，修复记录与回归结果见 4.7 节。

### BUG-01（高 / 安全）文件工具路径穿越，可读写 `tmp/file` 之外的任意文件

- **位置**：[FileOperationTool.java](../../src/main/java/com/aftersales/agent/tools/FileOperationTool.java#L17)（`readFile`）与 [第 29 行](../../src/main/java/com/aftersales/agent/tools/FileOperationTool.java#L29)（`writeFile`）
- **现象**：`filePath = FILE_DIR + "/" + fileName` 直接拼接，未做规范化与前缀校验。
- **复现**：
  - `readFile("../../pom.xml")` 返回项目根目录 `pom.xml` 的完整内容；
  - `writeFile("../../穿越-xxx.txt", "越界写入")` 在项目根目录成功创建文件，返回 `File written successfully to: .../tmp/file/../../穿越-xxx.txt`。
- **期望**：非法文件名返回 `Error reading file: ...` / `Error writing to file: ...`，且不创建文件。
- **影响**：`@Tool` 参数来自模型，提示词注入即可让智能体读取 `src/main/resources/application-local.yml`（含 DashScope/SearchAPI 真实密钥）、项目源码或写入任意位置，属于高危可达面。AI_CONTEXT §5.4 明确要求"新增工具必须限制参数取值范围与可访问资源，并做路径/域名校验"，当前实现与该约定冲突。
- **建议**：`Paths.get(FILE_DIR).toAbsolutePath().normalize()` 作为基准目录，`resolve(fileName).normalize()` 后校验 `startsWith(baseDir)`；同时拒绝绝对路径、`..` 段与非法分隔符。
- **对应用例**：`TC-TOOL-006`、`TC-TOOL-009`。

### BUG-02（高 / 安全）PDF 生成工具同样存在路径穿越

- **位置**：[PDFGenerationTool.java](../../src/main/java/com/aftersales/agent/tools/PDFGenerationTool.java#L26)
- **现象**：`filePath = fileDir + "/" + fileName` 未校验；`generatePDF("../越界-xxx.pdf", ...)` 返回 `PDF generated successfully to: .../tmp/pdf/../越界-xxx.pdf`，文件落到 `tmp/` 下。
- **影响**：与 BUG-01 同理，可写任意可达路径（例如覆盖配置文件、写入启动目录）。
- **建议**：与 BUG-01 共用统一的"安全文件名"校验工具。
- **对应用例**：`TC-TOOL-015`。

### BUG-03（中 / 功能）联网搜索结果少于 5 条时整段搜索失败

- **位置**：[WebSearchTool.java](../../src/main/java/com/aftersales/agent/tools/WebSearchTool.java#L42)
- **现象**：`organicResults.subList(0, 5)` 在结果数 < 5 时抛 `IndexOutOfBoundsException`，被 `catch (Exception)` 捕获后返回错误文案。
- **复现**：mock 返回 3 条 `organic_results`，`searchWeb` 返回 `Error searching Baidu: toIndex = 5`。
- **期望**：返回实际命中的 3 条结果；0 条时返回明确的"无结果"提示。
- **影响**：长尾、精确的售后问题（如具体快递公司理赔规则）经常只有 1-4 条结果，此时搜索能力完全不可用，且模型会误以为"搜索失败"，可能导致编造或直接转人工。
- **建议**：`subList(0, Math.min(5, organicResults.size()))`，并对 `organic_results` 缺失/为 null 做空值判断。
- **对应用例**：`TC-TOOL-019`。

### BUG-04（低 / 健壮性）`generatePDF` 内容为 null 时抛未封装异常

- **位置**：[PDFGenerationTool.java](../../src/main/java/com/aftersales/agent/tools/PDFGenerationTool.java#L43)，`catch` 只捕获 `IOException`（[第 48 行](../../src/main/java/com/aftersales/agent/tools/PDFGenerationTool.java#L48)）
- **现象**：`generatePDF("x.pdf", null)` 抛出 `IllegalArgumentException: Text content cannot be null.`，异常穿透到 `ReActAgent.step()` 被记为 `ERROR`，用户侧看到"步骤执行失败"。
- **期望**：工具契约应始终返回可读文本（成功或 `Error generating PDF: ...`），由模型决定下一步。
- **建议**：入参校验（null/空白）并捕获 `RuntimeException`，统一返回错误文案。
- **对应用例**：`TC-TOOL-013`。

### BUG-05（低 / 潜在安全）文件对话记忆 `conversationId` 可路径穿越

- **位置**：[FileBasedChatMemory.java](../../src/main/java/com/aftersales/agent/chatmemory/FileBasedChatMemory.java#L84)
- **现象**：`new File(BASE_DIR, conversationId + ".kryo")` 未校验；`add("../escaped-memory", ...)` 会在记忆目录之外创建 `escaped-memory.kryo`。
- **影响**：该组件当前默认未启用（`AftersalesApp` 使用内存记忆），风险暂时不可达；一旦按注释启用，`chatId` 来自 HTTP 查询参数，攻击者可读写任意 `.kryo` 路径。
- **建议**：对 `conversationId` 做白名单（`[A-Za-z0-9_-]{1,64}`）或哈希后再作为文件名。
- **对应用例**：`TC-MEM-007`。

### BUG-06（中低 / 设计）`BaseAgent` 执行结束后状态不复位，实例不可复用

- **位置**：[BaseAgent.java](../../src/main/java/com/aftersales/agent/agent/BaseAgent.java#L92)（`finally cleanup()`）与 [第 216 行](../../src/main/java/com/aftersales/agent/agent/BaseAgent.java#L216)（空实现的 `cleanup`）
- **现象（修复前）**：`run()` / `runStream()` 结束后 `state` 停留在 `FINISHED`（或 `ERROR`），`cleanup()` 未复位。同一实例第二次调用会抛 `Cannot run agent from state: FINISHED`。
- **回归用例**：`TC-AGENT-018`（修复后验证同一实例可再次 `run`，且上一轮消息已清理）。
- **影响**：`AftersalesAgent` 是 `@Component` 单例 Bean；`AiController` 通过 `new AftersalesAgent(...)` 规避了该问题，所以 HTTP 路径目前不受影响。但任何对单例的直接复用（现有 `AftersalesAgentTest` 再加一个测试方法、后续新增的调度/批量任务）都会失败；`messageList` 也会跨轮累积。
- **建议**：在 `cleanup()` 中把状态复位为 `IDLE`、清空步骤计数（保留/清空消息需按需求决定），或把 `AftersalesAgent` 声明为 `prototype`，并在文档中明确"实例单次执行"的约束。

| RISK-05 | 低（SSE 契约） | [BaseAgent.java](../../src/main/java/com/aftersales/agent/agent/BaseAgent.java#L156-L164) | 异常分支只发送 `执行错误：...` 后 `complete()`，**没有发送 `[DONE]`**；前端智能体模式会额外显示"连接中断"错误条。建议在 `finally` 或异常分支同样发送 `[DONE]`。 |
| RISK-06 | 低（健壮性） | [BaseAgent.java](../../src/main/java/com/aftersales/agent/agent/BaseAgent.java#L119-L121) | 校验阶段的 `catch (Exception e) { sseEmitter.completeWithError(e); }` 后没有 `return`，仍会继续设置 `RUNNING` 并执行任务，向已完成的 emitter 发送数据会再次抛异常。建议 `return`。 |
| RISK-07 | 低（代码整洁） | [AiController.java](../../src/main/java/com/aftersales/agent/controller/AiController.java#L100-L104) | `AftersalesAgent` 既声明为 `@Component` 单例，又在控制器里每次 `new` 一个实例；单例 Bean 实际未使用，且每次请求都会重建 `ChatClient`。建议二选一（若保留单例需先修 BUG-06）。 |

## 6. 现有测试质量评估（TEST-01）

现有 7 个测试类（`src/test/java/...`）没有发现任何缺陷，但它们**无法提供有效保障**：

1. **6/7 是 `@SpringBootTest`**：`AftersalesAppTest`、`AftersalesAgentTest`、`AftersalesDocumentLoaderTest`、`FileOperationToolTest`、`WebSearchToolTest`、`AftersalesAgentApplicationTests`。每次启动完整容器都会初始化向量库：17 个片段各调用一次模型做关键词增强，再逐条向量化（约 25 秒、约 34 次 API 调用），仅仅为了 `contextLoads` 或构造一个 `FileOperationTool`，成本高且强依赖网络与密钥。
2. **断言只到 `assertNotNull`**：`FileOperationToolTest`、`WebSearchToolTest`、`PDFGenerationToolTest`、`AftersalesAppTest`、`AftersalesAgentTest` 均只断言非空。而工具在失败时也返回非空错误字符串（如 `Error searching Baidu: ...`），所以**工具完全不可用或用例路径错误时，测试仍然通过**。
3. `AftersalesDocumentLoaderTest.loadMarkdowns()` 没有任何断言，`contextLoads()` 也没有断言。
4. `AftersalesAgentTest` 使用单例 `aftersalesAgent` 且只调用一次 `run()`；若再加一个测试方法，会因 BUG-06 直接失败。
5. `WebSearchToolTest` 与 `AftersalesAppTest.doChatWithMcp` 依赖真实外部服务，密钥缺失/失效时结果不确定。

**建议**：将本次新增的 20 个测试类作为回归基线（全部离线、无费用）；原集成测试改为 `@Tag("integration")` 并只在需要密钥的流水线运行，同时补充内容断言（引用规则原文、工具结果、PDF 文本等）。
